## fix(notifications): réarmer tous les rappels au démarrage, sans se fier au stockage du plugin

Labels : bug · Jalon : Épic 2 — notifications

**Objectif**
Qu'un rappel perdu par le système (Forcer l'arrêt, fermeture agressive du constructeur) soit reprogrammé à la prochaine ouverture de l'app.

**Constat**
Audit de Fable du 2026-09-24, point vérifié dans le code sur `main` (69bff98).
- `getPending` lit le stockage du plugin (SharedPreferences), jamais les alarmes système (`@capacitor/local-notifications` 8.3.1, `LocalNotificationsPlugin.kt:209-214`)
- `syncAllReminders` ne fait rien si ce stockage égale la liste voulue (`src/app/reminders-sync.ts:57-67,118`)
- Sur Android ≤ 14, après un Forcer l'arrêt, les alarmes sont perdues mais le stockage est intact : rien ne réarme
- Le test « quand le système a perdu les alarmes » (`reminders-restoration.integration.spec.ts:194-211`) simule la perte en vidant le stockage, l'inverse du réel
- `getPending` renvoie `schedule.at` en chaîne Java (`Thu Sep 24 09:00:00 GMT+02:00 2026`, `LocalNotification.kt:235`), pas en `Date` ; `pendingTime` (`due-reminders-schedule.ts:82-85`) peut donner `NaN`, ce qui fausse la comparaison et le calcul du plafond

**Critères d'acceptation**
- [ ] Au démarrage à froid, tous les rappels sont reprogrammés sans condition ; au retour au premier plan, la comparaison actuelle reste
- [ ] Test réécrit : stockage du plugin intact, alarmes perdues → rappels reprogrammés au démarrage
- [ ] L'instant prévu voyage dans `extra` en millisecondes et c'est lui qui est comparé ; le type `at` est corrigé ; test avec la vraie chaîne renvoyée par le plugin
- [ ] Coût vérifié avec 400 rappels (reprogrammation par lots)

**Notes**
- #41 (restauration) repose sur la même détection

## question(analytics): « statistiques anonymes » alors qu'un abonné est identifié

Labels : question · Jalon : Épic 12 — analytics

**Constat**
Audit de Fable du 2026-09-24, point vérifié dans le code sur `main` (69bff98).
- L'interrupteur et l'écran de consentement disent « statistiques anonymes » (`fr.json:396,502`)
- À la connexion, `auth.store.ts:40` appelle `identify(session.userId)` : l'UUID Supabase est un pseudonyme, pas une donnée anonyme (`conformite-play-store-rgpd.md:314` le reconnaît)

**À trancher** (question à Gaelle)
- Recommandation : retirer `identify` et garder l'identifiant aléatoire de PostHog : la promesse « anonymes » tient, moins de données personnelles, et rien dans le produit n'a besoin de relier statistiques et compte
- Alternative : garder `identify` et remplacer « anonymes » par « d'usage », ce qui permet d'analyser par abonné mais affaiblit la promesse
- La politique de confidentialité (#86) suit le choix
