# Flux de travail par tickets GitHub

- Les tickets sont les issues du dépôt, groupées par épic (0 Fondations → 12 Analytics). Commencer par les tickets en tête d’épic qui ne dépendent d’aucun écran
- Tickets en parallèle : un agent par ticket, chacun dans un worktree git isolé sur sa branche dédiée (`feat/…`, `fix/…`, `chore/…`, `docs/…`) créée depuis `main` à jour
- Les tickets d’un même lot ne touchent pas les mêmes fichiers ; un seul touche `package.json` / `pnpm-lock.yaml`
- Chaque agent reçoit un brief : les critères d’acceptation du ticket, les fichiers qu’il possède, les fichiers interdits, les commandes de vérification (`pnpm lint && pnpm type-check && pnpm exec vitest run && pnpm build-only`), les règles git
- **Agents en parallèle, ressources partagées** : chaque agent reçoit son propre port de vérification et le lance avec `pnpm exec vite --port 51xx` (jamais `pnpm dev -- --port`, dont le `--` littéral est ignoré par Vite qui démarre alors sur 5173). Personne ne tue le port 5173 ni ne lance `pkill -f` (le motif tue aussi le shell qui le porte) : on arrête un processus par son PID, après avoir vérifié son dossier de travail. Chaque agent écrit ses scripts et captures dans un sous-dossier à son nom du dossier temporaire, jamais à sa racine partagée, et utilise un profil Chromium et un port de débogage dédiés
- Avant de proposer un ordre de merge, fusionner toutes les branches du lot dans un worktree jetable et y lancer les commandes : c'est là que se voient les conflits entre branches et les faux positifs qu'aucune branche seule ne montre (le 2026-09-13, le placeholder « Ex. Bravecto » d'une branche cassait le contrôle de build d'une autre)
- Un second agent relit le diff de la branche contre les critères du ticket et CLAUDE.md ; les constats Critical / Important repartent chez l’implémenteur, puis re-revue ciblée du fix ; les mineurs sont notés dans la PR
- La PR s’ouvre **après revue propre, sans attendre que Gaelle la demande** (voir CLAUDE.md, section Git). Son corps : Quoi / Vérifié / Points à garder en tête ; toute décision prise faute de précision dans le ticket y est listée, et elle a d’abord été posée en question à Gaelle, ou consignée dans son journal en mode autonomie (voir `collaboration.md`). Une branche dont une question reste sans réponse attend, sans PR
- Le corps d'une PR qui livre un ticket commence par **`Closes #N`** (mot-clé GitHub, en anglais) : « Ferme #N » n'est pas reconnu, et onze tickets livrés sont restés ouverts le 2026-09-09 à cause de ça. Un ticket partiellement couvert se cite sans mot-clé (« Avance #N »)
- **Toute PR vise `main`, jamais une autre branche.** Une PR empilée, mergée depuis GitHub, atterrit dans sa base et jamais dans `main` — c'est arrivé avec #126 le 2026-09-09, le code de #15 est resté bloqué dans la branche de la maquette. Une dépendance sur une maquette ou une autre branche se règle en mergeant celle-ci d'abord, ou en acceptant que le diff montre ses fichiers en attendant. Après chaque série de merges, vérifier `main` (fichier clé présent, nombre de tests) avant d'annoncer « tout est mergé »
- Après le lot : retirer les worktrees temporaires (branches conservées), donner à Gaelle la liste des PR et l’ordre de merge conseillé
